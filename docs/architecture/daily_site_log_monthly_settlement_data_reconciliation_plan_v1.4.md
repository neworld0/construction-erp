# 공사일보·월 정산 데이터 전환 및 대사 계획 v1.4

> 정밀 검증 반영: V-01~V-04, V-06, V-07. 기존 원천의 중복 집계·법인 혼입·마감 후 직접 변경을 허용하지 않는다.

> **v1.3 전환 방침:** 과거·현재 공사일보를 이관하거나 FIELD에게 새로 작성시키지 않는다. 기존 원천으로 프로젝트별·법인별·그룹별 보고서를 재현하고, 검증을 통과한 기준일만 스냅샷으로 고정한다.

> **v1.4 이력 대사:** 기존 현장보고서(`FieldReport`)는 자동 공사일보 합계에 포함하지 않는다. 제출·승인 이력이 남은 경우 HQ·CEO의 `기존 현장보고` 이력으로만 대사하며, 신규 보고서 작성 건수는 0으로 관리한다.

## v1.3 보고서 재현·대사 절차

| 순서 | 대상 | 수행 | 통과 기준 |
|---:|---|---|---|
| 1 | 프로젝트별 원천 | 프로젝트·계약법인·기준일로 진행률·출역·원가·자재투입·재고를 읽기 전용 추출 | 모든 행이 하나의 법인·프로젝트에 귀속 |
| 2 | FIELD 공사일보 | 프로젝트별 자동 집계 결과와 원천 행 수·금액·수량을 비교 | 원천 ID 누락/중복 0건 |
| 3 | HQ 법인 취합 | 같은 기준일의 프로젝트 보고서를 합산하고 프로젝트별 소계와 비교 | 합계 = 프로젝트별 소계 합계 |
| 4 | CEO 그룹 취합 | 아산·미산 법인 보고서를 각각 산출한 뒤 합산 | 법인 필터별 값이 독립적이고 그룹합산만 두 법인 합계 |
| 5 | 마감 스냅샷 | 기준일·원천 컷오프·계산 버전·payload hash 기록 | 재생성 값과 해시·총액이 일치 |

### 금지·예외

- `SiteDailyLog` 입력 데이터나 과거 PDF를 새로운 원천으로 대량 등록하지 않는다.
- 보고서에서 발견한 오류는 해당 진행률·출역·원가·자재투입 원천의 정정 절차로만 해결한다.
- 프로젝트 미배정 FIELD 사용자, 타 법인 HQ, 권한 없는 CEO 조회 범위는 결과 0건과 접근 거부를 모두 검증한다.

## 1. 목적과 범위

이 계획은 `7월정산서.xlsx`의 업무 구조를 참고해 현재 ERP 원천 데이터로 정산서를 재생성하기 위한 것이다. 첨부 Excel의 수식·외부 링크를 그대로 이식하거나, PDF 공사일보를 무검증 일괄 등록하는 작업은 범위에 포함하지 않는다.

## 2. 원천별 처리 원칙

| 자료 영역 | Excel/PDF의 의미 | ERP 원천 | 처리 원칙 |
|---|---|---|---|
| 공사현황 | 계약·변경계약·실행예산·보험료 | Project, ProjectContract, BudgetItem, ContractChange | 계약 법인과 VAT 기준을 먼저 검증 |
| 기성·선급금·수금 | 기성액, 선급금 공제, 미수금 | BillingReport, ProgressBilling, AdvancePayment, CashEvent | 청구·발주처 확정·세금계산서·수금의 날짜를 분리 |
| 입출금 | 거래처별 수입/지출 | CashEvent, ExpenseExecution, BillingSettlementAllocation | 실제 현금일과 발생일을 혼동하지 않음. 발주처 직불은 CashEvent가 아닌 비현금 정산 |
| 미지급금 | 미지급 비용과 지급계획 | CostActual + PayableItem + BusinessPartner | 검수·사용 확정일 기준으로 발생. 회사 CashAccount와 거래처 지급계좌를 구분 |
| 자금청구 | 지급 요청 | ExpenseExecution/PayableItem | 계좌정보는 보호된 거래처 계좌 참조만 사용 |
| 하도급정산 | 하도급 기성·지급·직불 | SubcontractAgreement/Certificate/Claim/PayableItem | 계약·검수기성·청구·지급을 분리. 계약 없는 일반 거래처 비용과 분리 |
| 공사일보 진행률 | 계획·전일·금일·누계 | DailyProgress, ProjectWorkProgressMapping, WBSItem, ScheduleTask | 과거 PDF는 검토용. 보고서는 승인된 진행률 원천만 표시하며 별도 일지 물량을 실적 원천화하지 않음 |
| 자재반입 | 현장 입고 | Transfer/InventoryLedger RECEIPT | 자재 투입과 별개로 재고 증가 처리 |
| 장비·인원 | 일일 가동·공수 | EquipmentLine/Timesheet | 인원은 Timesheet 원천을 우선 |

## 3. 사전 데이터 품질 점검

1. 프로젝트 코드·계약 법인·현장창고·기준월의 일치 여부
2. 계약금액의 VAT 포함/별도, 보험료 포함/제외 기준
3. 거래처명 정규화 및 동일 거래처 중복 식별
4. CBS/계정과목 매핑 누락 및 프로젝트 예산 범위
5. WBS-일정작업 매핑과 물량/수기 진행률 계산방식의 중복 여부
6. 외부 통합문서 참조와 `#REF!` 수식 제거 대상 식별
7. 원가 발생액·지급액·발주처 직불액의 분리 및 CostActual 중복 합산 여부
8. 재고 기초·반입·투입·반송·기말수량 대사
9. 월마감 상태 및 마감후 정정 원천 확인
10. 발생일·증빙일·지급예정일·실제지급일의 기간 귀속 일치 여부
11. VAT 공제상태·적격증빙·사업관련성·공급가/VAT/총액의 일치 여부
12. 발주처 직불의 기성 미수금·미지급금 동액 상계와 CashEvent 미생성 여부
13. 하도급 계약·검수기성·청구·지급 상태의 혼입 여부

## 5. 차이 처리 원칙

- 원본 Excel 총액과 ERP 총액이 다르면 Excel 수식을 수정해 맞추지 않는다. 차이의 원천 거래, VAT 기준, 직불 여부, 기간 귀속을 식별한다.
- 과거 마감월은 원가·재고·현금을 직접 수정하지 않는다. Adjustment/정정 및 새 정산 버전으로 처리한다.
- 거래처 계좌, 연락처, 개인 성명은 대사 문서와 로그에서 마스킹한다.
- 계약 법인이 다른 거래는 다른 법인 정산으로 임의 합산하지 않는다.
- 발주처 직불은 회사 현금흐름에 입금·출금으로 포함하지 않되, 별도 비현금 직불 정산 지표로 표시한다.
- VAT 검토중 건은 총액 기준 잠정 원가로 표시하고, 세무 확정 전 VAT 신고 집계에는 포함하지 않는다.

## 6. 운영 검증 체크리스트

- [ ] 프로젝트별·법인별 월 정산서가 다른 법인 수치를 포함하지 않는다.
- [ ] 기성청구액, 선급금 공제, 수금, 미수금의 산식이 스냅샷과 일치한다.
- [ ] 자재 반입은 재고 증가, 자재 투입은 재고 감소 및 승인 원가 생성으로 분리된다.
- [ ] 공사일보 인원·자재투입 요약은 기존 원천과 정확히 한 번만 연결된다.
- [ ] 미지급금 잔액은 발생액 - 실제 지급 - 직불액과 일치한다.
- [ ] 확정 정산 출력은 원천 데이터·대사 결과·승인자·생성시각을 추적할 수 있다.


## v1.2 개정 범위 — AI Layer 연계 준비(설계 전용)

이 문서의 v1.2 개정은 `Construction_ERP_AI_Layer_Implementation_Design_Pack_v1.3`의
법인 범위, SoR 단일권위, 금액 의미, Evidence·Claim 재현성, 승인·마감 보존 원칙을
공사일보·월 정산 확장 설계에 연결한 것이다. **이번 버전은 AI 호출, AI 테이블,
마이그레이션, 외부 Provider 연결, 기존 업무 화면의 코드 구현을 포함하지 않는다.**

- 기존 ERP 원천 시스템(SoR)이 계약·진행률·원가·재고·노무·기성·승인·마감의 유일한
  확정 권위를 가진다. AI/Ontology는 향후 읽기 전용 Context, Evidence, 설명·검토·초안에만 사용한다.
- 모든 향후 Context는 `legal_entity_id`, 범위(`PROJECT`/`LEGAL_ENTITY`/`GROUP`),
  사용자·역할·법인 멤버십·프로젝트 배정의 권한 스냅샷을 먼저 확정한다. 프로젝트 범위는
  반드시 해당 프로젝트의 계약 법인과 일치하고, GROUP 범위는 명시적 그룹 권한이 있어야 한다.
- 계약·기성·원가·현금·세금 Claim에는 `amount_basis`(VAT 포함/별도/해당없음), 통화,
  기준일, 계산 서비스, 원천 스냅샷 해시를 함께 보존한다. 기준이 없는 핵심 금액 Claim은 생성·적용하지 않는다.
- 재무·계약·세금·승인·마감에 관한 핵심 Claim은 Claim ID와 Evidence link를 반드시 가져야
  하며, Evidence가 하나라도 없으면 향후 AI 결과의 적용·제출은 `BLOCK`한다. 일반 서술문은
  별도 관찰 지표로 관리하며 확정 사실로 승격하지 않는다.
- AI 초안의 기술 상태와 기존 문서의 HQ/CEO 승인·반려·잠금 상태를 분리한다. 승인 단일권위는
  기존 업무 workflow이며, AI/ontology의 장애·비활성화가 기존 업무를 중단시키지 않는다.

## 7. AI Layer 연계 준비 대사(데이터 무변경)

| 단계 | 수행 | 산출물 | 금지사항 |
|---|---|---|---|
| AR-D0 | 법인별 Project/Contract/Progress/Billing/Cost/Labor/Evidence/Approval/Closing 실제 SoR와 계산 서비스를 읽기 전용 인벤토리 | SoR Adapter Matrix | 모델·데이터 수정, 계약 법인 추정 |
| AR-D1 | 필드별 소유권(ERP 자동값/사람 입력/향후 AI 서술), 금액 기준, 기준일, VAT 정책, Generic Resolver를 확인 | Field Ownership·Amount Dictionary | 서로 다른 기성/세금계산서/수금 상태의 합산 |
| AR-D2 | 승인된 원천에서 Claim–Evidence 후보를 dry-run 생성하고 누락을 분류 | Claim Coverage Report | AI 호출, Evidence 자동 확정 |
| AR-D3 | 아산/미산/그룹합산, FIELD/HQ/CEO 권한별 redacted Context 범위를 재현 | Authorization Snapshot Report | 권한 밖 원문 Context 노출 |
| AR-D4 | 해시·캡처 시점·보존/파기·legal hold 정책을 대사 | Retention/Lineage Checklist | PII/계좌/주민번호 원문 보관 |

### 추가 대사 통과 기준

1. 핵심 재무·계약·세금·승인·마감 Claim 후보는 Evidence 연결률 100%이며, 미연결 항목은
   `BLOCK` 후보로 분류한다. 일반 서술문 Evidence 비율은 별도 관찰 지표로 기록한다.
2. 법인 미상, 프로젝트 미상, VAT 기준 미상, 기준일·계산 서비스 미상 레코드는 `NEEDS_REVIEW`로
   남기고 임의 보정·재분류하지 않는다.
3. 대사와 dry-run은 행 수·해시·조회 결과만 생성하며 기존 Project, DailyReport, CostActual,
   InventoryLedger, Timesheet, BillingReport, ClosingPeriod, Approval/Audit 기록을 변경하지 않는다.
4. AI Provider/Prompt/Response는 이 전환 범위에 포함하지 않는다. Provider 승인·DPA·보존 정책은
   외부 LLM 호출 전에 HQ·재무 책임자가 별도 승인한다.
