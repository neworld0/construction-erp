[FAST-CODEX] ATT-1 : 공통 Attachment 컴포넌트 구현 + 편집 가능 정책(DRAFT/REJECTED) 내장 + 한글 깨짐 상시 스캔 포함

당신은 시니어 Django 엔지니어입니다. 리포지토리 루트는 construction-erp 입니다. 

전제
- 기존 설계/모델/URL 유지
- DB 스키마 변경 금지
- ATT-0(Discovery/표준/한글 스캔)이 이미 진행되었으며, ATT-1은 “공통 컴포넌트”를 구현하는 티켓이다.
- 이후 ATT-2~ATT-5는 이 컴포넌트를 include해서 적용한다.
- 이번 추가 요구(첨부 변경 허용 정책)는 “공통 컴포넌트 수준”에서 표준으로 고정한다.

추가 요구(반드시 반영)
- 임시저장(DRAFT) 상태에서는 제출 전까지 첨부 파일을 추가/삭제/교체할 수 있어야 한다.
- 제출 후 반려(REJECTED) 처리되면:
  - 첨부 파일 수정/교체 가능(다시 제출 전까지)
- 제출(SUBMITTED) 및 승인(APPROVED) 상태에서는:
  - 첨부 변경 불가(조회만 가능)
- 마감(CLOSE-2) 잠금이 걸린 경우는 상태와 무관하게:
  - 첨부 변경 불가(조회만 가능)  ← 기존 규칙 우선

목표(산출물)
1) 공통 Attachment UI 컴포넌트 2종(상세/목록) + “편집 가능 정책” 내장
2) 첨부 변경(추가/삭제/교체) 버튼 노출 규칙이 모든 화면에서 동일하게 동작할 기반 제공
3) 한글 깨짐(UTF-8) 점검 포함
4) 이후 ATT-2~5에서 include만으로 첨부 UX + 편집 정책이 일관 적용 가능

------------------------------------------------------------
1) Discovery (필수, 코드 작성 전)
------------------------------------------------------------
다음을 먼저 확인하고 docs/ATTACHMENTS.md에 간단히 기록한다.

- 첨부 저장/연결 방식:
  - 공통 Attachment/Evidence 모델인지
  - object_type/object_id 기반인지
  - 도메인 모델이 직접 FileField인지
- 첨부 업로드/삭제/교체가 이미 가능한 엔드포인트/뷰가 존재하는지
  - 있으면 재사용, 없으면 “버튼만” 먼저 만들지 말고 최소 엔드포인트를 함께 만든다(단, 스키마 변경 금지)
- 상태 코드 실제 값 확인:
  - DRAFT / SUBMITTED / APPROVED / REJECTED (또는 유사 값)
- “마감 잠금”을 판정하는 기존 함수/가드 위치(CLOSE-2) 확인

------------------------------------------------------------
2) 공통 Attachment 표준 + 편집 정책 구현 (핵심)
------------------------------------------------------------
2.1 공통 컴포넌트 파일 생성
A) 상세용 컴포넌트
- templates/components/attachments_panel.html

입력(context)
- attachments: list/queryset (없으면 빈 리스트)
- can_edit: bool  (첨부 변경 가능 여부)
- upload_url: str or None (첨부 업로드/교체 처리 URL)
- delete_url: str or None (첨부 삭제 처리 URL, 선택)
- object_label: str (선택, 표시용: “진행률/원가/보고서/출역”)
- help_text: str (선택: “제출 전/반려 후 수정 가능” 안내)

표시 규칙
- 이미지(jpg/png/webp/gif): 인라인 미리보기 + “원본 보기(새 탭)” 링크
- 비이미지: 파일 리스트 + 새 탭 링크(target=_blank)
- 첨부가 없으면 “첨부 없음”을 과하게 노출하지 말고, 섹션을 숨기거나 작은 문구로만 표시

편집 UI(이번 요구사항 반영)
- can_edit=True 이면:
  - “파일 추가/교체” 입력 UI 노출(다중 업로드 지원)
  - 기존 파일 행마다 (선택) “삭제” 버튼 노출
  - 안내 문구(기본):
    - “임시저장/반려 상태에서는 제출 전까지 첨부를 수정할 수 있습니다.”
- can_edit=False 이면:
  - 업로드/삭제 UI는 숨김(조회만)
  - (선택) 안내 문구:
    - “제출/승인/마감 상태에서는 첨부를 수정할 수 없습니다.”

주의
- 이 티켓에서 “상태 판정 로직”은 view에서 can_edit 플래그로 넘기고,
  템플릿은 그 플래그만 믿고 렌더한다(템플릿에서 상태코드 직접 해석 금지).

B) 목록용 컴포넌트
- templates/components/attachment_badge.html
- 입력: attachments
- 표시:
  - 첨부 1개 이상일 때만 표시
  - 이미지 포함 시 🖼 우선, 아니면 📎
  - 개수 표시(🖼 2 / 📎 1)
- 목록에서 썸네일 금지

2.2 can_edit 계산 규칙(서버측, 공통 유틸 권장)
- 공통 함수로 분리(권장): attachments/policy.py 또는 hq/field 공용 util
- 입력: object_status, is_closed_locked, role/permission
- 출력: can_edit bool

정책
- if is_closed_locked: can_edit=False
- else if status in (DRAFT, REJECTED): can_edit=True
- else if status in (SUBMITTED, APPROVED): can_edit=False
- 상태명이 다르면 실제 프로젝트 값에 매핑해서 적용

2.3 업로드/삭제 엔드포인트(이미 있으면 재사용)
- 이미 각 탭에서 첨부 업로드가 되는 구조라면:
  - 그 URL을 upload_url로 전달
  - 삭제가 있다면 delete_url도 전달
- 만약 “표시만 있고 업로드/삭제 엔드포인트가 화면별로 제각각”이면:
  - 이 티켓에서 “공통 엔드포인트를 새로 만드는 것”은 금지(범위 초과)할 수 있으니,
  - 최소로: 기존 엔드포인트를 래핑/호출할 수 있게 upload_url만 연결
- 어떤 경우든 서버는 can_edit가 false일 때 업로드/삭제 요청을 거부해야 한다(보안).

------------------------------------------------------------
