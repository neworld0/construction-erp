=====================================================
[LAB-4 목표]
=====================================================
승인된 출역부(Timesheet.APPROVED)와 제출된 급여 배부(PayrollAllocationBatch.SUBMITTED/APPROVED)를 기반으로
프로젝트별/월별/ CBS별 인건비 실적을 집계하고,
이를 KPI(T10-3) 계산에 포함시킨다.

원칙:
- 원본 데이터(Timesheet/PayrollAllocation)는 변경하지 않는다.
- 집계는 “표준 집계 함수/뷰”로 제공하고, 필요시 캐시 테이블(옵션)을 도입한다.
- KPI는 “원가 실적”에 인건비를 포함해야 한다.
- data_quality(OK/미정/추정) 규칙을 인건비에도 적용한다.

=====================================================
1) 집계 범위/정의 (필수)
=====================================================
인건비 실적(LaborActual) =

A) 현장 출역 인건비:
- Timesheet.status=APPROVED 인 것만 포함
- TimesheetLine.amount 합계

B) 급여 배부 인건비(월급):
- PayrollAllocationBatch.status IN ("SUBMITTED","APPROVED") 인 것만 포함
- PayrollAllocationLine.amount 합계

집계 차원:
- project_id
- period_year, period_month
- cbs_id (가능하면)  # 없으면 “기본 인건비 CBS”로 매핑

CBS 매핑 정책:
- TimesheetLine의 labor_role.default_cbs가 있으면 사용
- 없으면 “공통 CBS(예: LABOR-GENERAL)”로 매핑
- PayrollAllocationLine.cbs가 null이면 “공통 CBS”로 매핑
=> 공통 CBS는 기존 CBS 코드표에 존재해야 함.
  없다면: LAB-4에서 마이그레이션/seed로 1개 생성(또는 설정값으로 지정).
  예: code="LABOR-GENERAL", name="인건비(공통)"

3) 서비스/쿼리 함수 (필수)
=====================================================
apps/labor/services.py 또는 apps/kpi/services.py에 다음을 추가/수정:

함수 1) get_labor_actual_by_month(project_id, year, month) -> dict
- 반환:
  {
    "total": int,
    "by_cbs": [{"cbs_id":..,"cbs_code":..,"cbs_name":..,"amount":..}, ...],
    "sources": {
       "timesheet_total": int,
       "payroll_total": int
    },
    "data_quality": "OK|ESTIMATED|UNKNOWN"
  }

집계 로직:
- timesheet_qs = Timesheet(APPROVED, project=..., work_date in month)
  sum TimesheetLine.amount grouped by cbs (via labor_role.default_cbs else fallback)
- payroll_qs = PayrollAllocationBatch(status SUBMITTED/APPROVED, year/month)
  join PayrollAllocationLine for project=...
  sum by cbs (null -> fallback)
- 합산

CBS fallback 매핑 구현 방법:
- DB에서 CASE WHEN으로 처리하거나
- 파이썬에서 2단계 집계:
  1) role.default_cbs별 sum (null 포함)
  2) null은 fallback_cbs로 합산
MVP에서는 파이썬 후처리 허용(성능 이슈는 후속)

함수 2) get_labor_actual_range(project_id, start_date, end_date, granularity="month|week")  # T10-3-EXTRA 대응
- week 지원 시 ISO week 기준으로 bucketizing

=====================================================
4) data_quality 규칙(필수)
=====================================================
인건비 품질 배지 로직을 KPI 배지 규칙과 일치시켜라.

권장 규칙(현재 시스템에 맞춰 조정):
- 대상 월이 CLOSED:
   - PayrollAllocationBatch가 존재하고 status SUBMITTED/APPROVED이고,
   - Timesheet는 해당 월의 현장 입력이 "필요 수준" 충족(아래)하면 → OK
   - 그렇지 않으면 → ESTIMATED
- 대상 월이 OPEN:
   - UNKNOWN 또는 ESTIMATED (KPI 화면 정책에 맞춤)

Timesheet “필요 수준” (MVP 단순):
- APPROVED Timesheet가 1건 이상이면 충족
(후속: 현장별 일수 커버리지 기준)

위 규칙을 코드로 분리:
- compute_labor_data_quality(project_id, year, month) 함수

5) KPI(T10-3) 반영 (핵심)
=====================================================
기존 KPI 계산에서 “원가 실적(actual_cost)” 산식에 인건비를 포함:

예:
- actual_cost_total = costactual_total + labor_total + inventory_issue_cost(이미 반영이면 중복 주의)
※ 중복 주의:
- INV-5가 CostActual을 자동 생성하도록 구현했다면 자재 투입은 이미 costactual_total에 포함된다.
- 인건비는 별도 축으로 합산하되,
  만약 기존에 “인건비를 CostActual로도 입력하는 경로”가 있다면 중복 집계 위험:
  - 정책: 인건비는 LAB-2/3 기반으로만 집계(권장)
  - 또는 CostActual에 category/type이 있다면 type="LABOR"는 제외(정책 결정)
이번 티켓에서 “중복 방지 정책”을 명확히 구현:
- CostActual에서 labor 관련 입력이 없다는 전제면 단순 합산
- 있다면 CostActual에 cost_type을 추가하는 것은 큰 변경이므로, MVP에서는:
  - labor_total을 별도 KPI 카드로 보여주고
  - actual_cost_total에는 포함하되, CostActual labor 입력이 없도록 운영 가이드(TODO)
=> 현실적으로는 actual_cost_total에 포함하는 구현을 우선하고,
   “CostActual에 labor 입력은 금지” 안내를 UI에 경고로 추가(최소).

KPI 산출물에 추가 필드:
- labor_cost_total
- labor_cost_by_cbs (옵션)
- labor_data_quality
