# GROUP-ENTITY-DISCOVERY-01 발견·전환 설계 보고서

## 1. 조사 범위와 기준

이 보고서는 **읽기 전용** 조사 결과이다. 모델, 마이그레이션, 운영 데이터, 시드 데이터는 변경하지 않았다.

- 대상: 프로젝트·계약·예산·CBS/WBS·원가·창고·자재·노무·급여·금융·기성·매출·월마감·승인·감사·RBAC
- 현재 소스 기준: `60534df` (작업 트리에 기존 미반영 변경이 존재하므로, 이 식별자는 배포 기준선이 아니라 조사 시점 참고값이다.)
- 조사 시점 데이터베이스 마이그레이션: 현재 적용 상태이며, LABOR는 `0032_alter_officepayrollrun_status`까지 적용됨
- 시스템 점검: `manage.py check` 통과
- 회귀 검증: 마감·일일 진행률 승인·본사 급여대장 관련 테스트 25건 통과
- 비식별 현황 수치: [런타임 스냅샷](evidence/group_entity_discovery_runtime_snapshot.csv)

## 2. 확인된 사실

### 법인 모델·권한 경계

현재 소스에는 `LegalEntity`, `OrganizationGroup`, `UserLegalEntityMembership` 모델이나 이에 준하는 법인 범위 검증이 없다. 사용자 권한은 `UserProfile.role`(CEO/HQ/FIELD)과 `ProjectAssignment`으로만 구성된다.

조사 시점 역할 프로필은 CEO 1, HQ 23, FIELD 4이며, 활성 프로젝트 배정 기록은 1건이다. 이는 역할만으로는 법인별 접근을 안전하게 추론할 수 없다는 근거다.

따라서 현재의 HQ·CEO 권한은 법인 단위가 아니라 전사 단위이며, 프로젝트·원가·다운로드의 법인별 URL/API 차단도 구현되어 있지 않다. 법인 선택 UI를 먼저 붙이는 것은 보안 경계가 아니므로 금지한다.

### 프로젝트 중심 귀속

`Project`는 계약금액·공사유형·일정·상태를 보유하지만 계약 법인 필드가 없다. 다음 기록은 프로젝트 FK로 법인을 **유도할 수 있는 후보**다.

- 계약·예산·WBS·진행률·일일보고·보고서
- 원가실적·매출인식·기성·청구
- 출역부·현장 출역원장·노무 신고 파일
- 현장창고·자재투입·프로젝트 자재요청
- 프로젝트 마감·정정

그러나 현재 프로젝트 자체의 계약 법인이 확정되지 않았으므로, 이 후보들을 곧바로 아산이나 미산으로 자동 귀속해서는 안 된다.

### 독립 소유가 필요한 영역

- 중앙창고는 프로젝트 FK가 없어 소유 법인을 별도 확정해야 한다.
- 일용 근로자와 본사 직원은 고용 법인 필드가 없다. 이름·로그인·현장 배정만으로 고용 법인을 추론할 수 없다.
- 본사 급여대장, 급여 배부 배치, 월마감은 현재 전사 단위 연월 유일성이다. 법인별 연월 유일성으로 개편해야 한다.
- 현금계좌·현금흐름·비용집행 중 프로젝트가 없는 기록은 법인 소유 증빙이 필요하다.

### 고위험 유일성 제약

| 영역 | 현재 제약 | 전환 원칙 |
|---|---|---|
| 월마감 | `(year, month)` | `(legal_entity, year, month)` |
| 본사 급여대장 | 활성 급여대장 `(year, month)` | 활성 급여대장 `(legal_entity, year, month)` |
| 급여 배부 배치 | `(year, month)` | `(legal_entity, year, month)` |
| 프로젝트 | `code` 전역 유일 | 그룹 공통 코드 정책 또는 법인 코드 접두어 정책을 HQ가 확정 |
| 중앙창고 코드 | `code` 전역 유일 | 그룹 공통 코드 유지 가능, 단 소유 법인은 필수 |

### 현재 데이터의 전환 결론

초기 조사만으로는 계약 명의·창고 소유·근로계약상 사용자·지급 주체를 확정할 수 없었다. 이후 HQ가 기존 프로젝트 계약 법인, 중앙·현장 창고 소유, 일용·본사 직원 고용 법인, 기존 급여대장·월마감 귀속을 모두 **㈜아산**으로 확정했다.

이 결정에 따라 프로젝트 및 그 파생 운영 기록은 아산 귀속 전환 대상으로 확정한다. 단, 프로젝트와 연결되지 않는 독립 현금·금융 기록은 소유 증빙이 별도로 필요하며, 과거 AuditLog는 법인 필드를 사후 덧쓰기하지 않고 보존한다. 상세 수량과 처리 기준은 [귀속 드라이런 매트릭스](evidence/group_entity_discovery_attribution_dry_run.csv)를 따른다.

## 3. 권장 데이터 경계

```text
ASAN-GROUP
├─ ASAN (㈜아산)
│  ├─ 계약 법인별 프로젝트
│  ├─ ASAN 소유 창고·재고·현금계좌
│  ├─ ASAN 고용 근로자·직원·급여·노무신고
│  └─ ASAN 월마감·세금·채권채무
└─ MISAN (㈜미산)
   ├─ 계약 법인별 프로젝트
   ├─ MISAN 소유 창고·재고·현금계좌
   ├─ MISAN 고용 근로자·직원·급여·노무신고
   └─ MISAN 월마감·세금·채권채무

GROUP MANAGEMENT (조회·대사)
└─ 법인별 수치 + 법인 간 거래 총액 + 제거 조정 + 관리 통합 수치
```

그룹 관리 화면은 두 원장을 합쳐 쓰지 않는다. 법인 간 거래의 원본 법인별 기록을 유지하고, 조회용 제거 데이터셋에서만 상계한다.

## 4. 권한 설계 판단

상세 매트릭스는 [권한 매트릭스](evidence/group_entity_discovery_permission_matrix.csv)에 있다.

- 법인 선택은 편의 기능이 아니라 서버 측 범위 검증의 입력값이다.
- CEO/그룹 HQ의 조회 권한은 승인 권한을 자동으로 부여하지 않는다.
- 시스템 master는 긴급 기술관리 계정일 뿐, 양 법인의 업무 승인·개인정보 일괄 열람 계정으로 설계하지 않는다.
- URL 직접 입력, API, CSV/Excel/PDF 다운로드에 동일한 법인 필터를 강제해야 한다.

## 5. 법인 간 거래 판단

상세 흐름은 [법인 간 거래 목록](evidence/group_entity_discovery_intercompany_catalogue.csv)에 있다.

다음은 기존 내부 이관·수정 화면으로 처리하면 안 된다.

1. 아산 창고에서 미산 현장으로 자재를 공급하는 경우
2. 한 법인의 직원·장비·관리 인력을 다른 법인의 프로젝트에 제공하는 경우
3. 아산이 원도급이고 미산이 조경 전문공종을 수행하는 경우
4. 한 법인이 다른 법인의 비용을 선지급하고 정산하는 경우

각 건은 공급 법인과 수취 법인의 대칭 기록, 증빙, 양측 승인, 마감 통제, 취소 시 역분개를 갖는 법인 간 거래로 구현해야 한다.

## 6. 전환·병행운영·복구 설계

### 전환 전

1. 데이터베이스 백업 및 모델별 건수·금액 스냅샷 생성
2. HQ가 프로젝트 계약 명의·창고 소유·고용 법인·금융 소유를 확정
3. `ASAN`, `MISAN`, `NEEDS_REVIEW` 귀속표 승인
4. 법인 마스터·권한·프로젝트 법인 귀속을 먼저 스테이징에서 검증

### 전환 순서

1. 그룹/법인/멤버십 기반 구현
2. 프로젝트·창고의 법인 소유 확정
3. 원가·재고·자재·노무·급여·마감의 법인 범위 검증 적용
4. 법인 간 거래 신설
5. 그룹 관리 대시보드 공개

### 병행운영

- 첫 한 달은 법인별 원장·재고·급여·마감 총액을 현행 기준과 매일 대사한다.
- 법인 간 거래는 초기에 자재 1건과 관리용역 1건을 통제된 시범 데이터로 검증한다.
- 불명확한 귀속 기록은 게시·수정이 아니라 HQ 검토 큐로 보낸다.

### 복구

- 전환 스크립트는 dry-run/apply를 분리하고 반드시 멱등적이어야 한다.
- 승인·마감·급여·세금 증빙 이력은 삭제하지 않는다.
- 전환 실패 시에는 임의 SQL 되돌리기가 아니라 사전 리허설한 백업 복원 또는 가역 마이그레이션으로만 복구한다.

| 면허 마스터 | 면허증·유효기간·허용 공종 | 경고 모드, 하드 차단 보류 |

## 8. 다음 구현 단계

다음은 `GROUP-ENTITY-FOUNDATION-01`이다. 다만 실제 데이터 귀속 마이그레이션은 위 HQ 확인표가 승인되기 전에는 수행하지 않는다.

프로젝트·창고·고용·마감의 실제 기존 데이터 귀속은 HQ 승인 후 별도, 가역적인 데이터 마이그레이션으로 적용한다.
